# MCP010 — Dangerous execution sink in Python server source

**Severity:** high · **Confidence:** medium
**OWASP MCP:** MCP05:2025 – Command Injection & Execution

## The risk

MCP008's sibling for Python, and it exists because MCP008 was blind to half
the ecosystem. The official `git`, `fetch` and `time` reference servers are
Python; so is every server in `awslabs/mcp`; so is FastMCP. A scan of
`awslabs/mcp` — 111 files, a monorepo of Python MCP servers — reported **two**
source files, because those were the only two that were not Python.

Like MCP008, this is pattern matching over raw text, not data-flow analysis.
It reports that a sink *exists* in the server's source; it cannot prove that
the value reaching it came from a tool call. That is the rule's defining
limitation, and why it is `confidence: medium` and `high` rather than
`critical`.

## What it flags

Three families, with three different trigger conditions, because what makes
each dangerous is different.

### 1. String executed as code — fires unconditionally

```python
eval(expression)
exec(source)
```

There is no version of these that belongs in a tool server. Same judgement
MCP008 makes about `eval()` and `new Function()`.

### 2. Shell — fires only when the command is *built*

```python
os.popen(f"psql -c 'SELECT * FROM {table}'")      # f-string
os.system("rsync -a %s %s" % (src, dst))          # % formatting
subprocess.check_output(f"git log {rev}", shell=True)
subprocess.run("tar czf out.tgz " + path, shell=True)
```

For `subprocess.*` the `shell=True` is required as well — without it the
string is not parsed by a shell and there is nothing to inject into.

The command has to be assembled from parts: an f-string, `+` concatenation,
`%` formatting, or `.format()`. A fixed string is not flagged (see below).

### 3. Deserialisation that runs code while decoding — fires by function

```python
pickle.loads(blob)
pickle.load(fh)
marshal.loads(blob)
yaml.load(text)          # only when no Loader= is passed
```

This family has no equivalent in MCP008 because it barely exists in
JavaScript, and its trigger is different in kind. `pickle.loads` executes
constructor code contained in the payload *as part of decoding it* — the
danger is the call itself, not how its argument was written, so argument shape
is not consulted. `yaml.load` is the exception: an explicit `Loader=` is the
documented way to make it safe, so a call that passes one is cleared.

## Clean example

```python
subprocess.check_output(["psql", "-c", f"SELECT * FROM {table}"])
subprocess.run(["rsync", "-a", src, dst], check=True)
yaml.safe_load(text)
```

Arguments as a list with no shell: the f-string is still interpolated, but
nothing parses `;` or `$()` out of it, because no shell is involved.

## What this rule does NOT flag

- **A fixed shell command.** `os.system("rsync --version")` and
  `subprocess.call("ls -la | wc -l", shell=True)` are shell calls with nothing
  interpolated into them. There is no injection point.
- **`subprocess` without `shell=True`.** An argument list is the correct way to
  spawn a process, and it is not weakened by building one of its elements from
  an f-string.
- **A bare variable as the command** — `os.system(cmd)`. A variable says
  nothing about where its value came from, and firing on it would flag every
  server that assembles argv in a helper function. This is deliberate
  under-detection, matching MCP008's treatment of `exec(cmd)`, and it is
  recorded as an accepted false negative below.
- **`cursor.execute(f"SELECT ...")`.** SQL injection is a real problem and a
  different one; this rule is about process and code execution. The
  `(?<!\.)` guard exists specifically for this — the AWS MySQL and Postgres
  MCP servers are full of `cursor.execute`, and without it this rule's real
  findings would be buried under them.
- **`yaml.load(text, Loader=yaml.SafeLoader)`** — explicitly safe.

## Known accepted false negatives

- **A sink reached through an alias.** `from subprocess import run` followed by
  `run(cmd, shell=True)` has no `subprocess.` prefix to match, and
  `from os import system` the same. Python's `from x import y` is far more
  common than the JavaScript equivalent, so this misses more here than the same
  limitation does in MCP008.
- **A command built in a variable and passed in.** See above.
- **No proof the argument derives from a tool call's arguments.** The same
  defining limitation as MCP008. The
masking preserves offsets and newlines, so reported line numbers stay exact.

This is not a nicety. Before it existed, a scan of `awslabs/mcp` — 1161 real
Python files — produced exactly one finding, and it was the comment

> `# Instead of using exec(), we'll use a function factory approach`

in a file whose entire point was that it does **not** call `exec`. One finding
on real input, and it was noise. The regression corpus made that concrete, and
the fix is cheap in Python because `#` comments and string literals are easy to
delimit.

MCP008 has the same weakness for TypeScript and still accepts it — it is why a
self-scan of this repository flags MCP008's own source. That remains a separate
decision.

## How to fix

- Pass arguments as a list and leave `shell=False` (the default):
  `subprocess.run(["git", "log", rev])`. Nothing parses shell metacharacters
  out of a list element.
- If a shell is genuinely required, validate every interpolated value against
  a strict allowlist, and use `shlex.quote()` rather than hand-built quoting.
- Replace `eval`/`exec` with a dict mapping known-safe names to functions.
- Replace `pickle` with `json` for anything crossing a trust boundary, and
  validate the decoded structure against an expected schema.
- Replace `yaml.load` with `yaml.safe_load`.

## How to suppress

```
# mcpscan-disable-next-line MCP010 -- mandatory reason
```

Without the `--` and the reason, the suppression is ignored and becomes an
`info` finding for "malformed suppression" — silencing without a written
justification is not supported. See [MCPSCAN001](MCPSCAN001.md).

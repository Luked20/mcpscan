# MCP005 — Unconstrained command parameter

**Severity:** high · **Confidence:** medium
**OWASP MCP:** MCP05:2025 – Command Injection & Execution

## The risk

Like MCP004, this rule detects a **risk surface**, not a payload: a schema
that permits something dangerous, whether or not the handler actually does
anything unsafe with it. That is why it is `confidence: medium` — the
`severity` the rule declares is `high`, not `critical`, because the engine's
confidence ceiling caps what a `medium`-confidence rule may claim (see
`docs/SPEC.md` §6.1), and because a schema shape, unlike an embedded
payload, is not unambiguous evidence of a vulnerability by itself.

A tool that runs a command, a shell, or a script needs some way for the
caller to say *what* to run. If that parameter is a bare `string` or
`array` with no `enum`, `const`, or `pattern`, the schema does not stop it
from carrying shell metacharacters (`;`, `|`, `` ` ``, `$(...)`) or an
entirely different command than the one the tool's name promises. Whether
that becomes an actual command injection depends on how the handler invokes
it — `execFile('git', [userArg])` is safe from shell parsing regardless;
`exec(`git ${userArg}`)` is not — but the schema alone gives no evidence
either way, which is exactly the surface this rule flags.

## Vulnerable example

```json
{
  "name": "run_command",
  "description": "Runs a command on the host.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "command": { "type": "string" }
    },
    "required": ["command"]
  }
}
```

`command` accepts any string. If the handler passes it to a shell (`exec`,
`system`, backticks) rather than `execFile`/`spawn` with an argument array,
`"ls; rm -rf /"` runs the second command as freely as the first.

## Clean example

```json
{
  "name": "run_predefined_command",
  "description": "Runs one of a small set of predefined commands.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "command": { "type": "string", "enum": ["ls", "pwd", "whoami"] }
    }
  }
}
```

`command` can now only ever be one of three literal values — there is no
string to inject into, because there is no string, only a closed choice.

## What this rule does NOT flag

- **A parameter name outside the fixed list.** Only `cmd`, `command`,
  `shell`, `script`, `exec`, `bash`, `sh`, `powershell`, `args`, or `argv`
  (case-insensitive, exact match) count. `commandline_flags` does **not**
  match — the regex is anchored (`^...$`), so a longer identifier that
  merely contains one of these words is not enough. See `run_report` in
  `tests/fixtures/MCP005/clean/tools.json`.
- **A constrained value.** An `enum`, `const`, or `pattern` on the property
  satisfies this rule, same as MCP004. For an `array` parameter (e.g.
  `args`), a `pattern` on `items` also counts — `args` itself carries none
  of the three keys, but each element it can contain is constrained, which
  is what actually matters for a list of arguments. See `run_with_args` in
  the clean fixture.
- **A non-string, non-array type.** `command` typed `number` — e.g. a MIDI
  command code sent to a device — is not flagged; neither is `command`
  typed `object` (a structured, already-parsed pipeline description). See
  `send_key` and `run_pipeline` in the clean fixture.
- **No `inputSchema` at all.** Nothing for this rule to inspect.

## How to fix

- Prefer an `enum` of the exact permitted commands. This is almost always
  possible for a purpose-built tool — "run one of these five git
  subcommands" is a closed set, not open-ended shell access.
- If the tool genuinely needs arbitrary arguments, split it into typed
  fields instead of one free-form string: an `operation` enum for *what* to
  do, plus an `args` array whose `items` carry a `pattern` for what each
  argument may look like.
- **However the schema ends up shaped, execute with `execFile`/`spawn`
  and an explicit argument array — never a shell string.** With no shell in
  the middle, `"; rm -rf /"` passed as one argument is a literal, inert
  string the target program receives verbatim, not a second command a shell
  parses and runs.

## How to suppress

```
// mcpscan-disable-next-line MCP005 -- mandatory reason
```

Without the `--` and the reason, the suppression is ignored and becomes an
`info` finding for "malformed suppression" — silencing without a written
justification is not supported.

# MCP004 — Unconstrained path parameter in a file tool

**Severity:** high · **Confidence:** medium
**OWASP MCP:** MCP02:2025 – Privilege Escalation via Scope Creep

## The risk

MCP001–003 detect a **payload**: text that should not be in a tool
definition at all, so their confidence is `high`. MCP004 detects a **risk
surface** instead — a schema that *permits* something dangerous, whether or
not the handler behind it is actually careless. The code might resolve and
validate the path perfectly. The schema just doesn't prove it, which is why
this rule is `confidence: medium` and requires three conditions together
before it fires.

A tool that reads, writes, lists, or otherwise touches files needs a way to
say *which* file. If that parameter is declared as a bare `string` with no
`pattern`, `enum`, `const`, or `format`, the schema places no limit on what
gets passed: an absolute path outside the intended directory, or a relative
path containing `../` segments that walk out of it. An agent that has been
manipulated (by a poisoned tool description elsewhere, a compromised
upstream response, or a confused chain of reasoning) can pass anything a
`string` accepts — including `/etc/passwd` or `../../.ssh/id_rsa` — and the
schema will not stop it before it reaches the handler.

## Vulnerable example

```json
{
  "name": "read_file",
  "description": "Reads a file from disk and returns its contents as text.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" }
    },
    "required": ["path"]
  }
}
```

Nothing in `path`'s schema says where it may point. `path` could be
`/etc/passwd`, `../../../../root/.ssh/id_rsa`, or a UNC path — the schema
accepts all of them equally.

## Clean example

```json
{
  "name": "read_file",
  "description": "Reads a file from disk within the project root only.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": { "type": "string", "pattern": "^/project/[A-Za-z0-9_/.-]+$" }
    },
    "required": ["path"]
  }
}
```

The `pattern` doesn't make traversal impossible on its own (see "How to
fix"), but it proves the schema author *considered* the shape of a legal
path — and it is one of the four ways this rule accepts as a constraint. An
`enum` of allowed filenames or a `const` for a fixed path work just as well
when the tool only ever needs one of a small, known set of files.

## The scope exemption: a manifest that declares its own boundary

A file-reading tool *must* take a path — that is what it is for. Applied
literally, the three conditions below fire on every correctly built file
server, which makes MCP004 a tax on the whole category rather than a signal.

The regression corpus (`docs/SPEC.md` §8.2, `tests/corpus/`) demonstrated
exactly that on the first run: the official
`@modelcontextprotocol/server-filesystem` produced **nine** `high` findings —
`read_text_file`, `write_file`, `move_file`, `list_directory`,
`get_file_info`, and the rest — while doing the one thing that actually
works, validating every path in the handler against an allow-list of roots
given at startup.

That server says so in its own tool descriptions:

> Read the complete contents of a file from the file system as text.
> **Only works within allowed directories.**

So: **when any tool in a manifest explicitly declares a directory
restriction, every path parameter in that same manifest file is exempt.** The
declaration has to be explicit — a restrictive framing (`only works`,
`must be`, `restricted`, `confined`, `sandboxed`), a permission word
(`allowed`, `permitted`, `approved`, `whitelisted`), and a directory noun,
all in one sentence. Prose that merely mentions a directory ("The directory
is resolved relative to the project root.") is not a declaration and does not
exempt anything.

**Why the whole manifest and not just the tool that said it.** The allow-list
is a property of the server process, not of one tool — the same handler
enforces it for everything the server exposes. Checking per tool would clear
`read_text_file` and still flag `read_file`, the deprecated one-line alias
directly above it in the same file, with the same parameter, protected by the
same handler, whose description has no room for the claim. A report that
contradicts itself inside one file costs more trust than the finding is
worth. The unit is the manifest file — the same "one file is one deployment"
rule MCP006 uses.

This is why MCP004 is `appliesTo: 'target'` and not `'tool'`: it has to see
every tool in a file before it can judge any of them.

## What this rule does NOT flag

All **three** of the following must hold for a finding to fire; missing any
one of them makes it noise, so the rule stays silent:

1. **The parameter name doesn't look like a path.** Only
   `path`, `file`, `filename`, `filepath`, `dir`, `directory`, `target`,
   `source`, `dest`, or `destination` (case-insensitive, exact match) count.
   A `query` parameter on a file-reading tool is not flagged — see
   `read_file_contents` in `tests/fixtures/MCP004/clean/tools.json`.
2. **The parameter is already constrained.** A `pattern`, `enum`, `const`,
   or `format` on the property — of any kind, not evaluated for
   strength — satisfies this rule. MCP004 does not judge whether the
   `pattern` is a *good* one; it only checks that the schema author put a
   fence up at all. (A weak pattern is a code-review problem, not something
   a schema-shape rule can detect.)
3. **The tool itself isn't a file tool.** A `path` parameter on
   `build_url` — "Builds the request URL." — is not flagged: nothing in the
   tool's name or description suggests it touches the filesystem. This is
   the condition that keeps the rule from firing on every parameter named
   `path` across a whole codebase, most of which have nothing to do with
   files (URL builders, Kubernetes tools, routing, etc.).

Also does **not** flag:

- **A non-string type.** `path` typed `number` (e.g. a numeric file
  descriptor) is not a bare string and is not flagged.
- **No `inputSchema` at all.** A tool with no schema has nothing for this
  rule to inspect.
- **A file mention far from a file verb.** "Returns the number of open
  network connections. See also the file-based variant." contains the word
  "file", but not near enough to a verb like "read"/"write"/"open"/"list" to
  read as a file tool — the rule requires the two within a few words of each
  other, not merely both present somewhere in the description.

- **Any path parameter in a manifest that declares a directory
  restriction** — see the scope exemption above.

See `tests/fixtures/MCP004/clean/tools.json` for the full set of these
near-misses as concrete fixtures, and
`tests/fixtures/MCP004/clean/scoped-server/tools.json` for the scope
exemption. The latter is deliberately a *separate file*: the exemption is
manifest-wide, so putting those tools in `tools.json` would have exempted
every other clean case in it and the fixture would have passed for the wrong
reason.

## Known accepted false negative

- **A manifest can state a restriction it does not enforce.** One sentence
  matching the pattern above, anywhere in the file, exempts every path
  parameter in it — including a tool added later that the allow-list does not
  actually cover. This rule reads what a server *declares*; confirming that
  the handler enforces it means running the server, which is `--connect` and
  out of MVP scope (`docs/SPEC.md` §7.1). It is the same standing limit
  §14 states for every pattern matcher here: against someone who has read the
  rules, this does not hold. Measured against real servers, the alternative
  was nine false positives on the most widely used MCP server there is, and a
  scanner that cries wolf on the reference implementation does not get run
  a second time.

## How to fix

- Add a `pattern` anchored to an allowed root directory (e.g.
  `^/data/[A-Za-z0-9_-]+\\.json$`), or an `enum` of the exact filenames the
  tool is allowed to touch.
- **A schema `pattern` alone does not stop traversal after resolution** —
  `^/project/.*$` still matches `/project/../../../etc/passwd` as a string,
  even though `path.resolve()` sends it outside `/project`. Validate in the
  handler too: resolve the path, then confirm the resolved path still starts
  with the permitted root, before touching the filesystem.

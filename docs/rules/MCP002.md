# MCP002 — Invisible Unicode character in tool definition

**Severity:** critical · **Confidence:** high
**OWASP MCP:** MCP03:2025 – Tool Poisoning

## The risk

An MCP tool's `name` and `description` are a privileged channel: the model
reads that text in full in every prompt where the tool appears, but the human
reviewing the server — in the PR diff, in the terminal, in an MCP client —
usually only sees the rendered text. Invisible Unicode characters (zero-width,
tags, direction overrides) don't show up in that rendered text, but they're
still there for the model. That makes it possible to embed an instruction,
tool name, or payload the human will never review — the same class of attack
as Trojan Source (CVE-2021-42574), applied to the tool-description layer
instead of source code.

A scanner that flags `critical` on legitimate text — Persian, Devanagari,
Arabic, emoji with ZWJ — loses the user's trust on the first run. That's why
this rule doesn't treat "invisible character" as a binary category: it flags
by class **and** by context. See `docs/SPEC.md` §7.2 for the full policy
table.

## Vulnerable example

```json
{
  "name": "read_file",
  "description": "Reads a file from disk.\u{E0049}\u{E0067}\u{E006E}\u{E006F}\u{E0072}\u{E0065}"
}
```

The last six codepoints are *tag characters* (U+E0000–U+E007F) — invisible in
any renderer, and used here to spell out "Ignore" inside the description the
model reads. There is no legitimate use of tag characters in tool text: the
rule always flags them when they appear.

## Clean example

```json
{
  "name": "read_file",
  "description": "Reads a file from disk and returns its contents."
}
```

## What this rule does NOT flag

This section is the central point of the document: if you got an MCP002
finding on text that doesn't look malicious, it's because the case below
doesn't yet cover yours — open an issue with the example, don't silence the
rule without reviewing it first.

- **Emoji with ZWJ (U+200D).** `Faz deploy 👩‍💻 rapido` or `👨‍👩‍👧 🏳️‍🌈` do not
  trigger. Every "composed" emoji sequence (profession + person, family, flag)
  uses U+200D to glue the base emoji into a single sequence — that's how
  Unicode defines these emoji, not an obfuscation technique.
- **Persian and Devanagari with ZWNJ (U+200C).** `می‌شود` (Persian) and `क्‌ष`
  (Devanagari) do not trigger. Zero-width non-joiner is **required spelling**
  in these scripts — removing the ZWNJ changes the word, it's not an "extra"
  space.
- **Balanced bidi isolates (U+2066/2067/2068 … U+2069).**
  `اقرأ ⁨read_file⁩ ملف` does not trigger. FSI…PDI (or LRI…PDI, RLI…PDI) is the
  mechanism UAX #9 recommends for embedding an identifier written in another
  direction (e.g. a Latin tool name) inside Arabic/Hebrew text without messing
  up the visual order of the surrounding characters. It only triggers when
  **unbalanced** — an opener without a closer, or vice versa.
- **Balanced bidi embeddings (U+202A/202B … U+202C).** Same logic as the
  isolates: `valor ‪read_file‬ final` (LRE…PDF) does not trigger while
  balanced.
- **U+200E (LRM) and U+200F (RLM).** Pure directional marks, with no visual
  width and no reading ambiguity — routine use in bidirectional text. They
  never trigger, in any context.
- **A single variation selector (U+FE0F etc.).** `Marca ❤️ concluído.` does
  not trigger — the U+FE0F there just means "render as a colored emoji", the
  normal use of the character. Only a **run of 3 or more** consecutive
  variation selectors triggers.
- **ZWJ/ZWNJ between non-Latin characters.** What makes a ZWJ/ZWNJ suspicious
  isn't the character itself, it's appearing **between two ASCII/Latin
  letters or digits** (`read‌file` has no spelling reason to have a ZWNJ in
  the middle) — or at the ends of the string, where there's no neighbor left
  to "join". Between emoji, or between Arabic/Indic letters, it's normal
  usage and does not trigger.

## How to fix

Remove the invisible character from the tool's `name`/`description`. To find
out which character it is, run:

```bash
node -e "
const fs = require('fs');
const text = fs.readFileSync(process.argv[1], 'utf8');
for (const ch of text) {
  const cp = ch.codePointAt(0);
  if (cp > 0x7f && !/[\p{L}\p{N}\p{P}\p{S}\p{Zs}]/u.test(ch)) {
    console.log('U+' + cp.toString(16).toUpperCase().padStart(4, '0'), JSON.stringify(ch));
  }
}
" path/to/tools.json
```

If the finding is a genuine false positive — a legitimate use case the policy
above doesn't cover yet — fix the rule (`src/rules/mcp/MCP002.ts`) instead of
suppressing it individually; a false positive on a `critical` rule is a
product bug, not expected noise.

## How to suppress

```
// mcpscan-disable-next-line MCP002 -- mandatory reason
```

Without the `--` and the reason, the suppression is ignored and becomes an
`info` finding for "malformed suppression" — silencing without a written
justification is not supported. See [MCPSCAN001](MCPSCAN001.md).

# MCP008 — Dangerous execution sink in server source

**Severity:** high · **Confidence:** medium · **OWASP MCP:** `MCP05:2025 – Command Injection & Execution`

## The risk

`eval()`, `new Function(...)`, and a shell command built from interpolated text (`child_process.exec`/`execSync` fed a template literal or a string concatenation) all execute content that is assembled at run time rather than fixed at write time. In an MCP server, the values that end up in that assembled string very often trace back to a tool call's arguments — arguments an agent (and, transitively, whatever the agent is following instructions from) controls. When they do, this is remote code execution.

**This rule is pattern matching over raw source text, not data-flow analysis.** It flags that a dangerous sink *exists* in the file — it does not, and structurally cannot, prove that a tool argument actually reaches that sink. A `child_process.exec` call built from a template literal is exactly as risky whether or not any of its interpolated values ever originate from `request.params.arguments`; conversely, a template-literal `exec()` built entirely from values the process itself controls (no attacker input anywhere in the chain) is not exploitable at all. The rule cannot tell those two cases apart. That is exactly why this is a **risk-surface** rule (`docs/SPEC.md` §7.3) at `confidence: 'medium'`, not a payload rule at `high`/`critical` — it detects a shape that permits danger, not a proven exploit path. See `docs/SPEC.md` §7.4 for the accepted misses this implies.

## What it detects

- `eval(...)` — the string-to-code sink.
- `new Function(...)` — the same sink in constructor form.
- `child_process.exec(...)` where the argument is a **template literal** or a **string concatenation** — not a plain string literal.
- `execSync(...)` (including `child_process.execSync(...)`) under the same condition.

Only source files whose language is `ts` or `js` are inspected. **Test files are never inspected at all** — the collector (`discover()` / `isTestFile()` in `src/collect/source.ts`) skips any path with a `tests/`, `test/`, `__tests__/`, `__mocks__/`, or `spec/` directory segment, or a `*.test.*`/`*.spec.*` basename, before a `SourceFile` is ever produced. A sink inside test code never runs in front of an agent, so it is not a deployed sink and not a real finding — see `docs/SPEC.md` §7.4.

## Vulnerable example

```ts
export function runUserExpression(userInput: string): unknown {
  return eval(userInput);
}

export function compileDynamic(src: string): Function {
  return new Function('x', src);
}

export function listFilesUnsafe(dir: string): void {
  child_process.exec(`ls ${dir}`);
}

export function backupUnsafe(name: string): void {
  execSync('tar -cf ' + name + '.tar ' + name);
}
```

All four fire independently: `eval`, `new Function`, `exec` with a template literal, and `execSync` with a concatenated string.

## Clean example

```ts
export function listFilesSafe(dir: string): void {
  execFile('ls', [dir]);           // argument array, not a shell string
}

export function statusSafe(): void {
  spawn('git', ['status']);        // argument array, not a shell string
}

export function checkoutSafe(): void {
  child_process.exec('git status'); // constant string literal
}
```

`execFile`/`spawn` pass arguments as an array — there is no shell string to inject into, so they're outside this rule's scope entirely. `exec('git status')` is a fixed string with nothing interpolated into it.

## What this rule does NOT flag

- **`execFile(...)` or `spawn(...)` with an argument array**, e.g. `execFile('ls', [dir])`. There is no shell command string being assembled — the array form is exactly the safe pattern this rule's remediation recommends.
- **`exec(...)`/`execSync(...)` called with a plain, constant string literal**, e.g. `exec('git status')`. Nothing is interpolated into it.
- **A bare, unqualified `exec(...)` call** with no `child_process.` prefix. `exec` alone is too common a name (any promise-based wrapper, test helper, unrelated function) to anchor a security finding on; only the qualified `child_process.exec(` form is in scope. (`execSync` has no such collision risk and is matched unqualified.)
- **The word "eval" as part of a longer identifier** — `evaluate(...)`, `myEval(...)`. Anchored so that "eval" must be immediately followed by `(` (optionally with whitespace); a longer identifier never satisfies that.
- **`.eval(...)` as a property access on an object**, e.g. `sandbox.eval(code)`. A dot immediately before `eval` excludes it — this is a real method named `eval` on some object, not a call to the global `eval` function.

## Known accepted false negatives (docs/SPEC.md §7.4)

- **No data-flow proof.** As stated above, the rule cannot tell a sink fed by attacker-controlled input from one fed entirely by trusted constants. Both fire; neither is confirmed exploitable by this rule alone.
- **Sinks hidden behind indirection.** `const run = eval; run(x)`, a sink reached through a re-exported alias, or one assembled via `globalThis['ev' + 'al'](x)` are all invisible to text pattern matching.
- **Comments naming a sink.** Not flagged: `//` and block comments are blanked before the patterns run, preserving offsets and newlines so line numbers stay exact. A comment mentioning a sink is the realistic noise source for a rule like this — MCP010's first run over 1161 real Python files produced exactly one finding, and it was a comment saying the author had *avoided* `exec`.
- **Strings containing sink-shaped text.** String *contents* are blanked too, so a sink named in test fixture data, in a security check, or in a warning message does not fire.

  This was not the original design. Strings were left unmasked because a regex literal such as `/["']/` contains a quote that starts no string, and telling a regex literal from a division needs a parser this rule does not have. A scan of [`czlonkowski/n8n-mcp`](https://github.com/czlonkowski/n8n-mcp) settled it: **four findings out of five were string contents**, and none was a sink —

  | Line | What it actually is |
  |---|---|
  | `jsCode: 'const result = eval(item.json.code);'` | test fixture data |
  | `code?.includes('eval(')` | a security check looking *for* eval |
  | `'Avoid eval() - it is a security risk'` (×2) | a warning message |

  The last two come from that project's own dangerous-pattern validator, which strips strings and comments before running its checks. It had solved this exact problem, and this rule flagged the warning text of the solution.

  The regex-literal hazard is handled with two defences rather than a parser: regex literals are recognised and skipped using the previous-significant-character heuristic (`= /re/`, `: /re/`, `(/re/`), and every quoted-string mask is bounded to its own line — which `'` and `"` literals cannot cross anyway — so a fooled heuristic damages one line, not the file.
- **Non-`ts`/`js` sources.** A Python MCP server's own dangerous sinks (`subprocess.run(shell=True, ...)`, `eval`, `exec`) are entirely out of scope for this rule; `SourceFile.language` other than `'ts'`/`'js'` is skipped.
- **`execFile`/`spawn` given a shell-joined string instead of an array**, e.g. `spawn(fullCommandString, { shell: true })`. The array-vs-string distinction this rule relies on to clear `execFile`/`spawn` doesn't hold once `shell: true` reintroduces a shell.

## How to fix

Pass the command and its arguments separately to `execFile`/`spawn` — no shell, no string building — instead of interpolating values into a shell command string. If a shell is genuinely required, validate every interpolated value against a strict allowlist before it reaches the command string.

```diff
- child_process.exec(`ls ${dir}`);
+ child_process.execFile('ls', [dir]);
```

For `eval`/`new Function`, replace with an explicit, statically-defined allowlist of the behaviors actually needed — never evaluate arbitrary text as code.

```diff
- return eval(userInput);
+ const handlers: Record<string, () => unknown> = { /* known-safe operations */ };
+ return handlers[userInput]?.();
```
